Goal:
Make FlowDeck the single authoritative completion/evidence layer across both:
1. native FlowDeck orchestration
2. integrated CPTR control-plane supervisor/director flows

The control plane may collect or project evidence, but it must NOT become a second independent verifier, completion authority, retry ledger, lease authority, or execution owner.

Core invariant:

CPTR owns model/tool execution.
FlowDeck owns authoritative orchestration completion/evidence truth.

Target architecture:

Control API / Supervisor
        ↓
FlowDeck durable logical identity
        ↓
CPTR / qualified FlowDeck execution
        ↓
trusted runtime observations
        ↓
canonical FlowDeck evidence contract
        ↓
FlowDeck verifier/completion policy
        ↓
authoritative terminal state
        ↓
control-plane status projection only

Do not create a second model/verifier/tool loop.

2. Classify all verification/completion sources

B. Control-plane projection/reference

- director success decisions

3. Define one canonical evidence contract

Reuse existing FlowDeck evidence semantics.

Authoritative evidence may come only from trusted observations such as:
- structured CPTR tool result
- independent filesystem postcondition
- tester exit/result evidence
- browser/runtime observation
- hermetic Git result
- durable reconciler result
- authenticated approval result where policy allows

Non-authoritative evidence:
- agent prose
- supervisor prose
- director prose
- model self-report
- "done" claims
- model-generated logs
- stale evidence
- inferred success
- evidence from another operation/user/workspace/attempt

4. Bind authoritative evidence to durable identity

Every authoritative evidence item must bind to the relevant:
- authenticated user
- workspace
- FlowDeck run
- step
- logical operation
- physical attempt where applicable
- specialist/worker
- operation fingerprint
- fencing epoch where applicable
- evidence type
- verifier/source
- timestamp

Evidence from one durable identity must never satisfy another.

5. Make control-plane completion derive from FlowDeck truth

For any control scope/task that depends on FlowDeck execution:

Control-plane SUCCESS must require FlowDeck authoritative success.

The control plane must never independently translate:

FAILED → SUCCEEDED
OUTCOME_UNKNOWN → SUCCEEDED
MANUAL_REVIEW_REQUIRED → SUCCEEDED
CANCELLED → SUCCEEDED
NOT_RUN → SUCCEEDED

If FlowDeck and control-plane state disagree:
- FlowDeck wins
- control-plane state must converge to FlowDeck
- disagreement must not create success

6. Adapt control-plane verification

Audit the integrated verification service.

Preferred behavior:

control observation
    → evidence adapter
    → FlowDeck evidence API
    → FlowDeck verifier

Do not retain an independent "verification succeeded therefore task succeeded" pathway.

If control-plane verification logic is useful, convert it into:
- evidence producer
- evidence formatter
- policy adapter

not a final authority.

7. Mutation completion

Preserve existing coding semantics:

intent
→ active physical attempt
→ valid workspace lease/fencing
→ mutation
→ independent postcondition
→ authoritative evidence
→ FlowDeck terminal outcome

Control supervisor must consume that outcome.

A normal tool return or agent response is insufficient.

8. Tester verification

Do not duplicate tester execution.

Control plane should consume existing structured tester evidence:
- check identity
- workspace/repository
- physical attempt
- exit code
- timeout state
- output bounds
- termination state

No arbitrary control-plane shell verification.

9. Git evidence

Use existing qualified hermetic read-only Git implementation.

Preserve:
- fixed read-only operations
- no shell
- no arbitrary args
- no network mutation
- no Git mutation

Any control-plane `diff_check` behavior must map into the canonical Git evidence path.

10. Browser evidence

Preserve the distinction:

browser operation succeeded
≠
model interpretation is verified fact

Only trusted runtime/browser observations can become authoritative evidence.

11. Retry/idempotency unification

Audit control supervisor retry logic.

Requirements:
- reuse FlowDeck logical operation identity
- retries create physical attempts, not unrelated logical mutations
- OUTCOME_UNKNOWN is never blindly retried
- duplicate request does not create duplicate mutation
- failure-signature logic cannot override FlowDeck recovery policy

12. Lease/fencing unification

FlowDeck remains the only authoritative workspace lease/fencing system.

Any stale supervisor or worker that loses the current fencing epoch must not publish authoritative completion evidence.

Do not create a second lease authority.

13. Cancellation

Cancellation must converge through FlowDeck durable truth.

After cancellation:
- future execution stops
- active uncertain side effects become OUTCOME_UNKNOWN when required
- stale worker completion is rejected
- control scope/task reflects FlowDeck outcome
- no late success override

14. Recovery/restart

On restart:
- reload FlowDeck durable state
- do not trust stale in-memory control state
- preserve logical operation and attempt identities
- preserve fencing
- preserve UNKNOWN
- do not rerun successful work unnecessarily
- do not blindly retry uncertain mutations

The supervisor must recover from FlowDeck durable truth.

15. Approval unification

Audit:
- FlowDeck approvals
- control-plane approvals

Execution-affecting approval must be:
- authenticated
- exact user/workspace
- operation/fingerprint bound
- one-shot
- scoped to permission to attempt

Approval does NOT prove successful execution.

Avoid two independent approval authorities for the same operation.

16. Control evidence storage

Do not delete existing control-plane evidence tables blindly.

Decide explicitly whether control evidence becomes:
- projection
- reference to FlowDeck evidence
- display/status summary

It must not remain a second source of final execution truth.

17. State mapping

Define deterministic mapping from FlowDeck terminal state to control-plane state.

At minimum:

FlowDeck SUCCEEDED
→ control succeeded

FlowDeck FAILED
→ control failed

FlowDeck CANCELLED
→ control cancelled

FlowDeck OUTCOME_UNKNOWN
→ control uncertain / manual action required

FlowDeck MANUAL_REVIEW_REQUIRED
→ control manual review required

Do not collapse uncertain/manual states into generic failure or success if their meaning is needed for recovery.
