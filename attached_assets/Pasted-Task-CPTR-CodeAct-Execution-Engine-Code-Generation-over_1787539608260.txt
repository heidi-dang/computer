Task
CPTR CodeAct Execution Engine — Code Generation over Tool Calling + Persistent REPL

Goal:

Implement a production-grade CodeAct execution mode in CPTR inspired by the Strands Code Agent architecture.

Instead of requiring the model to repeatedly emit individual structured tool calls such as:

read_file(...)
→ result returned to model
search_files(...)
→ result returned to model
read_file(...)
→ result returned to model

allow the model to generate one executable code block that composes qualified CPTR capabilities:

files = search_files("authentication")
results = []

for file in files:
    content = read_file(file.path)
    results.append(analyze(content))

summary = summarize(results)

The code executes inside a persistent, isolated REPL.

Intermediate values remain native runtime objects and DO NOT need to be serialized back into the LLM context after every individual operation.

Primary objectives:

1. Reduce token overhead.
2. Reduce model reasoning cycles.
3. Reduce latency for multi-step tasks.
4. Preserve intermediate data as native objects.
5. Allow expressive loops, filtering, branching, aggregation, retries, and composition.
6. Preserve all CPTR/FlowDeck security and authority boundaries.
7. Keep the existing native tool-calling engine available.
8. Never turn this into unrestricted host Python/shell execution.

This is NOT:

model
→ unrestricted Python
→ host OS

It MUST be:

model
→ generated CodeAct program
→ sandboxed persistent REPL
→ CPTR capability library
→ existing authenticated policy/tool boundary
→ actual CPTR implementation
→ evidence / result

Architecture target:

User
  ↓
Computer or Heidi
  ↓
CPTR model
  ↓
Execution planner
  ↓
CodeAct mode
  ↓
Generated Python program
  ↓
Persistent isolated REPL
  ↓
CPTR capability SDK
  ├── files.read(...)
  ├── files.search(...)
  ├── files.list(...)
  ├── browser.inspect(...)
  ├── git.status(...)
  ├── tests.run(...)
  └── other explicitly qualified capabilities
  ↓
existing CPTR implementations
  ↓
tool/runtime evidence
  ↓
native transcript / FlowDeck verification

The REPL is an execution composition layer.

It is NOT a new authority layer.

CPTR remains the model/tool execution owner.

FlowDeck remains orchestration, capability, workspace, lease/fencing, cancellation/recovery, evidence, and completion authority for Heidi work.

2. DO NOT REPLACE THE EXISTING AGENT ENGINE BLINDLY

Introduce CodeAct as another CPTR execution strategy.

Initial architecture:

ExecutionMode:
- TOOL_CALLING
- CODEACT

Do not immediately delete conventional tool calling.

Existing native agent behavior must continue working.

CodeAct should be introduced behind configuration/feature control until qualification is complete.

No client-side authority field should be able to bypass server policy.


3. BUILD A CPTR CAPABILITY SDK FOR THE REPL

Do NOT expose arbitrary internal Python modules.

Expose a narrow CPTR library.

Example conceptual API:

cptr.files.read(path)
cptr.files.list(path)
cptr.files.search(query, path=None)

cptr.git.status()
cptr.git.diff()

cptr.browser.snapshot()
cptr.browser.navigate(url)

cptr.tests.run(check_id)

The model should interact with these functions rather than raw tool-name JSON calls.

Every function MUST internally reuse the existing qualified CPTR implementation.

Do not duplicate filesystem, browser, Git, test, or other business logic inside the REPL layer.


4. CAPABILITY FUNCTIONS MUST PRESERVE AUTHORITY

Calling:

cptr.files.read(...)

inside CodeAct MUST have exactly the same or stricter authorization as invoking the existing read_file tool.

The REPL cannot bypass:

- authenticated user
- workspace ownership
- specialist role
- capability registry
- mutation policy
- FlowDeck lease
- fencing epoch
- operation identity
- approvals
- cancellation
- verification

The CodeAct runtime only improves composition.

It does not grant permission.


5. START READ-ONLY

First qualification should expose only low-risk read-oriented capabilities.

Initial recommended CodeAct library:

- read_file
- list_directory
- search_files
- qualified Git read operations
- browser read-only observation
- structured metadata/query helpers

Do NOT expose mutation in Phase 1.


6. PERSISTENT REPL

Implement a real stateful interpreter.

Within one CPTR task / FlowDeck physical attempt:

execution #1:

files = cptr.files.search("auth")

execution #2:

important = [f for f in files if f.path.endswith(".py")]

execution #3:

contents = [cptr.files.read(f.path) for f in important]

The variables:

files
important
contents

must remain available as native objects.

Do not serialize them back through model messages unless the model explicitly prints/summarizes them.


7. DEFINE THE PERSISTENCE LIFETIME EXPLICITLY

Do NOT create one global REPL.

Isolation unit should be approximately:

authenticated user
+ workspace
+ CPTR task / FlowDeck physical attempt

Recommended:

one REPL session per active execution attempt

not:

one Python interpreter shared by every user

Lifecycle:

ATTEMPT START
→ create REPL session

multiple generated code cycles
→ same REPL memory

attempt completion/cancellation/failure
→ destroy session

retry
→ new physical attempt
→ new REPL unless an explicitly safe durable state restoration design exists

Never restore arbitrary pickled interpreter memory across server restarts initially.


8. REPL STATE IS EPHEMERAL EXECUTION STATE

FlowDeck durable state remains authoritative.

Do not make Python memory the durable source of truth.

After process restart:

- durable operations come from database
- workspace truth comes from actual workspace
- REPL memory is gone
- recovery reconciles safely

Do not pretend lost REPL memory survived.


9. NATIVE OBJECT RETENTION

This is one of the main performance requirements.

Tool results called from CodeAct should be returned directly as useful Python objects where appropriate.

Avoid this:

function
→ JSON string
→ model
→ JSON parse
→ function

Prefer:

function
→ Python object
→ variable
→ subsequent Python operation

Design typed return objects where valuable.

Examples:

FileSearchResult
FileContent
GitStatus
BrowserSnapshot
TestResult

But avoid creating a huge unnecessary object framework.

Use lightweight dataclasses/typed structures where they improve composition.


10. MODEL ACTION FORMAT

When CodeAct is active, the model's primary action interface should be executable code rather than repeatedly selecting JSON tool calls.

The model should know:

- available modules/functions
- signatures
- docstrings
- capability restrictions
- examples
- execution limits

Do NOT dump implementation source into the prompt.

Generate concise capability documentation dynamically from the server-authorized capability set.


11. NO HIDDEN CAPABILITY DISCOVERY

The model must only see functions it can actually call.

For example a security-auditor REPL may expose:

cptr.files.read
cptr.files.list
cptr.files.search
cptr.git.status
cptr.git.diff

It must NOT even advertise:

cptr.files.write
cptr.shell.run
cptr.deploy
cptr.secrets
cptr.git.push

UNKNOWN → DENY remains mandatory.


12. SANDBOX THE INTERPRETER

This is mandatory.

Do NOT use unrestricted:

exec(model_generated_code, globals())

against the CPTR backend process.

The generated code is untrusted.

The REPL must execute in a contained environment.

Audit available sandbox mechanisms in the existing runtime and choose the strongest practical architecture.

Required restrictions include:

- import allowlist
- no arbitrary Python imports
- no subprocess unless explicitly mediated by a CPTR capability
- no os.system
- no socket/network access
- no raw filesystem access outside CPTR capability APIs
- no environment variable access
- no server process introspection
- no arbitrary sys.path traversal
- no dynamic package installation
- no native extension loading
- no unsafe serialization
- no ctypes
- no multiprocessing escape
- no arbitrary signal/process manipulation
- no introspection path that trivially escapes sandbox

Treat generated Python as hostile input.


13. IMPORT ALLOWLIST

Imports must be server-owned.

Potential safe standard-library subset may include things such as:

- math
- statistics
- collections
- itertools
- functools
- re
- json
- datetime

Only after explicit audit.

Do not permit arbitrary import.

The user/model cannot expand the allowlist.


14. CPTR SDK OBJECT MUST NOT LEAK INTERNALS

If exposing:

cptr.files

the implementation must not allow:

cptr.files.__dict__
cptr.files._internal_session
cptr.files.backend
etc.

to reveal powerful backend objects.

Use narrow proxy objects.

Avoid exposing database sessions, request objects, service instances, credentials, or filesystem handles into the interpreter.


15. CODE EXECUTION LIMITS

Every execution block needs limits:

- wall-clock timeout
- CPU limit where practical
- memory limit
- output size limit
- maximum generated code length
- maximum number of capability calls
- recursion protections
- maximum loops/steps where practical
- cancellation support

An infinite loop must not wedge the API worker.


16. CANCELLATION

The Stop button must terminate:

- FlowDeck run
- active child specialist
- active CodeAct execution
- pending capability call
- REPL session if necessary

Cancellation must not merely hide the UI.

Test:

while True:
    pass

then Stop.

The worker must terminate within a defined bounded interval.

22. CONTEXT REDUCTION

The key optimization:

Do NOT append every capability result to model history.

Inside CodeAct:

result = cptr.files.read(...)

should remain in REPL memory.

Return to the model only:

- stdout explicitly emitted
- execution errors
- bounded summaries
- explicitly requested observations
- capability exceptions needed for self-correction

Avoid flooding context with massive outputs.


23. TRACEBACK SELF-CORRECTION

When generated code fails safely:

NameError
TypeError
CapabilityError
etc.

return a bounded sanitized traceback to the model.

Allow it to produce a corrected code block.

Set a maximum repair-cycle count.

Do not allow infinite model-error loops.


24. MUTATION PHASE — ONLY AFTER READ-ONLY QUALIFICATION

Do not expose mutation until read-only CodeAct receives >=9/10 qualification.

Later mutation architecture:

model code
→ cptr.files.write(...)
→ FlowDeck logical operation
→ active lease/fencing
→ intent persisted
→ mutation
→ independent verification
→ authoritative evidence

A Python function call must not bypass the durable mutation engine.


25. SHELL

Do not expose arbitrary Python subprocess as the implementation of shell.

If shell is eventually exposed:

cptr.shell.run(qualified_command_id, ...)

must use CPTR's qualified shell boundary.

Do NOT expose:

subprocess.run(...)
os.system(...)
pty
shell=True

inside the REPL.


26. GIT

Keep existing Git protections.

Initially expose only qualified read-only operations.

No generated Python should be able to instantiate Git or call the git binary directly.

Later Git mutation remains separately gated.


27. BROWSER

Browser functions should wrap existing CPTR browser authority.

Generated code may compose browser observations, but must not gain arbitrary network/socket access.


28. MCP

Do NOT automatically convert every MCP tool into a Python callable.

MCP remains denied unless explicitly mapped and qualified.

UNKNOWN MCP → DENY.


29. FLOWDECK INTEGRATION

The specialist must not see all CodeAct capabilities.
