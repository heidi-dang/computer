3. Findings (worth surfacing)
Startup token reuse on Replit. artifacts/computer/replit-dev.sh and artifacts/api-server/replit-cptr-api.sh both bridge SESSION_SECRET → CPTR_STARTUP_TOKEN "so a workflow restart does not invalidate the setup screen." This means the one-time setup token is persistent and equal to the workspace's SESSION_SECRET. Anyone who can read that Replit secret (or who guesses it pre-setup) can call POST /api/auth/setup and become admin. The code in cptr/routers/auth.py::setup uses secrets.compare_digest (good), but the token's strength is then the strength of SESSION_SECRET rather than a fresh secrets.token_hex(32). Risk is real for first-time setup before the admin user is created.

Setup token is also printed to the console / embedded in the URL by cptr/cli.py::run (f"http://{display_host}:{port}/?token={token}"). Standard logger may capture it; URL tokens may end up in proxy/referrer logs. Once consumed by /api/auth/setup it is not invalidated elsewhere I can see (no explicit single-use marker in the auth router).

preinstall rm -f of lockfiles. package.json preinstall silently removes package-lock.json and yarn.lock and exits non-zero if invoked via npm/yarn. It is supply-chain hardening, but it is also destructive on a developer machine and is not gated by CI. If the wrong thing ever runs npm install it erases state.

High default iteration cap. CHAT_MAX_ITERATIONS=2048 and CLAUDE_CODE_MAX_BUFFER_SIZE=128 MiB in cptr/env.py. A runaway agent loop or a user-supplied prompt can produce large sustained load (potential DoS for a single-tenant CPTR). Audit-log body cap is 2 KiB (good), but the upstream request log has no body cap in this snippet.

CORS_ALLOWED_ORIGINS defaults to "*" (cptr/env.py line 125). On a multi-user / browser-accessible deploy this is too permissive. Override required for production.

auth.signup_enabled = true (DB-driven, default unknown). cptr/routers/auth.py::signup allows self-registration into a pending role; first PAM user is auto-promoted to admin. The promotion logic in auth.py:153-158 checks for any existing admin and gives admin only when none exists. That is correct, but a second PAM account created after the first admin will be promoted to user, not admin — confirm the intended behavior is "first admin wins."

SUPERVISOR_OPENAI_API_KEY and SUPERVISOR_OPENAI_MODEL are read from env without validation (cptr/env.py:117-118). If the CPTR_CONTROL_PLANE_ENABLED default is flipped, these will silently be sent to OpenAI.

No cp/shell-call sites with eval/exec observed in the FlowDeck/auth/runtime paths. The 50+ matches for eval|exec|os.system|subprocess are legitimate uses (e.g., asyncio.create_task, setup, code editor, subprocess.Popen in terminal). I did not read all of them.

.replit is treated as a "controlled" deployment (CPTR_FLOWDECK_MODE=controlled, GOVERNANCE=strict). With mode=controlled, EXECUTE_COMMAND/WRITE_FILES/MUTATE_GIT become live capabilities gated by grants. Confirm that production grants actually whitelist only intended workspaces, not the whole filesystem.

postMerge hook runs pnpm install --no-frozen-lockfile then pnpm --filter db push (scripts/post-merge.sh). The --no-frozen-lockfile defeats lockfile-integrity checks on every merge. The db push is a schema migration that runs without an explicit guard. If a malicious PR lands, it ships.
