# Make Heidi Better Than Replit — Priority Build Specification

The goal is not to copy Replit feature-for-feature.

The target is:

**Heidi should feel as easy as Replit for building an app, while being substantially stronger at autonomous engineering, debugging, verification, parallel execution, and user control.**

Core architecture:

```text
User
  ↓
Heidi
  ↓
FlowDeck orchestration
  ↓
Build Agent
  ↓
CPTR execution engine
  ├── CodeAct
  ├── native tools
  ├── browser
  ├── terminal/process manager
  ├── database
  └── preview
  ↓
Independent verification
```

Heidi remains the coordinator.

Build Agent performs implementation.

CPTR remains the sole execution authority.

FlowDeck remains orchestration, lifecycle, cancellation, evidence, and verification authority.

# 1. Idea → Working App

## Target

Heidi must be better than Replit at taking:

```text
"Build me an inventory management system."
```

and autonomously producing:

```text
requirements
→ architecture
→ database
→ backend
→ frontend
→ authentication
→ tests
→ live preview
→ browser verification
→ production build
→ verified result
```

The user should not need to manually choose frameworks, create folders, configure a dev server, wire a database, or repeatedly tell Heidi what to do next.

## Implement `/build`

When Heidi is selected:

```text
/build Build me an inventory management system
```

should trigger Build mode.

Flow:

```text
Heidi
  ↓
Understand product intent
  ↓
Generate implementation contract
  ↓
Inspect existing workspace
  ↓
Choose architecture
  ↓
Create Build DAG
  ↓
Execute Build tasks
  ↓
Run application
  ↓
Open preview
  ↓
Browser-test application
  ↓
Repair defects
  ↓
Verify requirements
  ↓
Return working app
```

## Product Brief

Before implementation, Heidi creates a lightweight internal product specification:

```text
Objective
User flows
Required screens
Data model
API requirements
Authentication
Responsive requirements
Acceptance criteria
```

Do not ask the user dozens of questions if sensible defaults can be safely inferred.

Only ask when a decision materially changes the product.

## Smart defaults

Heidi should detect the existing stack when a repository already exists.

For a new application, use configurable preferred stacks rather than model improvisation.

Example:

```text
Frontend preference
Backend preference
Database preference
Authentication preference
Package manager
Testing framework
Deployment target
```

Never hardcode these globally.

## App completion contract

Before building, define what "working" means.

Example:

```text
✓ app starts
✓ authentication works
✓ dashboard loads
✓ database persists data
✓ create/edit/delete works
✓ mobile layout works
✓ production build passes
✓ no browser console errors
```

Heidi cannot mark the job complete until the verifier checks the contract.

# 2. Autonomous Coding

## Target

The Build Agent should be capable of working for long periods without requiring repeated prompts.

It should execute:

```text
inspect
→ reason
→ modify
→ run
→ observe
→ repair
→ verify
```

until the objective is satisfied or a genuine user decision/approval is required.

## CodeAct as the primary Build execution mode

Use CodeAct for multi-step coding work.

Instead of:

```text
tool call
→ model
→ tool call
→ model
→ tool call
→ model
```

prefer:

```text
model
→ executable CodeAct program
→ multiple qualified CPTR operations
→ result
```

Persistent REPL state should survive across execution cycles within the same physical attempt.

This reduces:

```text
token usage
model round trips
context pollution
latency
```

The REPL remains sandboxed and has no authority beyond CPTR's qualified capabilities.

## Structured coding capabilities

Build Agent should receive APIs such as:

```text
code.search
code.symbols
code.references
code.definition

files.read
files.create
files.patch
files.move
files.delete

tests.run
build.run

browser.inspect
browser.screenshot
browser.console
browser.network

runtime.start
runtime.stop
runtime.logs
```

Prefer patches and symbol-aware edits over whole-file rewrites.

## Autonomous repair loop

After every meaningful implementation:

```text
change
→ typecheck
→ tests
→ build
→ runtime
→ browser
```

Failure:

```text
observe evidence
→ identify cause
→ repair
→ rerun exact failed verification
```

Do not pile more code on top of unexplained failures.

# 3. Parallel Build Execution

## Target

Heidi should outperform Replit by combining safe parallelism with stronger authority and verification.

Large tasks should become dependency-aware DAGs.

Example:

```text
                    Repository map
                          │
                  Architecture plan
                          │
          ┌───────────────┼───────────────┐
          ↓               ↓               ↓
      Backend          Frontend       Database
          │               │               │
          └───────────────┼───────────────┘
                          ↓
                     Integration
                          ↓
                       Tester
                          ↓
                      Reviewer
```

## Isolated Build worktrees

Every parallel mutation task must work in an isolated Git worktree.

Example:

```text
main
├── build/backend-01
├── build/frontend-01
├── build/database-01
└── build/testing-01
```

No two mutation agents should freely edit the same canonical workspace concurrently.

## Parallelize read-only work aggressively

Safe parallel tasks:

```text
Mapper
Researcher
Architect
Security Auditor
Dependency analysis
Test discovery
Browser observation
```

These should run concurrently whenever dependencies allow.

## Mutation scheduling

Mutation tasks may run concurrently only when their file/ownership boundaries are proven non-conflicting.

Otherwise FlowDeck serializes them.

## Merge specialist

Before combining independent Build tasks:

```text
compare common base
→ inspect both diffs
→ detect overlapping changes
→ resolve conflicts
→ run verification
→ integrate
```

Never use blind automatic merge as completion evidence.

## Dynamic DAG replanning

If:

```text
Frontend completed
Backend failed
```

Heidi should replan only the affected branch.

Do not restart the whole job.

# 4. Root-Cause Engineering

This should become one of Heidi's strongest advantages over Replit.

## Primary rule

**Never fix a symptom until the underlying failure path has been traced.**

Forbidden pattern:

```text
error
→ add fallback
→ add retry
→ add second state
→ add special case
→ original bug still exists
```

Required pattern:

```text
symptom
→ reproduce
→ trace
→ determine authoritative state
→ isolate failing boundary
→ identify root cause
→ minimal repair
→ regression test
→ full verification
```

## Root-Cause Debugger

Create a dedicated debugging workflow.

```text
User:
/debug steering gives Bad Gateway
```

Heidi performs:

```text
1. reproduce failure
2. capture request identity
3. inspect frontend request
4. inspect proxy
5. inspect API route
6. inspect service
7. inspect database state
8. inspect lifecycle transition
9. inspect child execution
10. correlate timestamps
11. identify first incorrect state
12. fix that state
```

## Evidence graph

For every defect, construct:

```text
Observed symptom
    ↓
Request/event
    ↓
Responsible component
    ↓
State transition
    ↓
Incorrect assumption/state
    ↓
Root cause
```

The agent should be able to report:

```text
Symptom:
502 Bad Gateway

Immediate failure:
LifecycleError escaped route handler

Why:
late child SUCCEEDED transition attempted after parent CANCELLED

Root cause:
child completion path lacked parent terminal-state fencing

Repair:
reject late child transition before lifecycle mutation

Regression:
cancel child while provider completion races
```

This is much stronger than "I changed several things and it works now."

## No speculative patch rule

If the cause is unknown:

```text
UNKNOWN
```

and continue investigation.

Do not start editing just because a probable cause exists.

## Differential debugging

When a feature previously worked:

```text
known-good SHA
vs
current SHA
```

Heidi should automatically inspect:

```text
relevant diff
changed dependencies
changed config
changed schema
changed runtime behavior
```

## Request tracing

Introduce correlation IDs across:

```text
frontend
→ API
→ FlowDeck
→ child task
→ CPTR execution
→ tool
→ DB
→ Socket.IO
```

One bug should be traceable as one lineage.

## State-machine inspection

Lifecycle bugs should be diagnosed against explicit state machines.

For example:

```text
PENDING
→ RUNNING
→ SUCCEEDED

PENDING
→ RUNNING
→ CANCELLED

RUNNING
→ OUTCOME_UNKNOWN
```

Illegal transitions should be captured as structured evidence.

## Root-cause acceptance requirement

A debugging task cannot be marked complete without:

```text
reproduction before fix
root cause identified
minimal fix
regression reproducer now passing
no fallback masking original failure
relevant full regression green
```

## Function-level tracing

For critical features:

```text
UI action
→ frontend function
→ API
→ service
→ persistence
→ background execution
→ event emission
→ frontend reconciliation
```

Audit the entire path.

## Authority audit

Heidi specifically checks:

```text
Who owns this state?
Who is allowed to mutate it?
Is there more than one source of truth?
Can stale child state overwrite parent state?
Can UI state become authoritative?
```

## Bug hunting

Audit should actively attempt to find:

```text

TOCTOU
double execution
orphaned processes
late events
lost updates
broken idempotency
reconnect duplication
stale caches
incorrect error conversion
silent fallbacks
```

not merely inspect code style.

After Build Agent says implementation is ready:

## Visual testing

Heidi should inspect:


## Console gate


## Network gate

Detect:

```text

403
404
409
422
```

# 10. Built-In Authentication

Authentication should be as easy as:

```text

```

but avoid CPTR lock-in.

## Auth provider adapters

Support configurable providers such as:

```text
Auth.js
Clerk
Supabase Auth
Firebase Auth
custom OAuth/OIDC
application-native auth
```

## Heidi chooses based on project context

Existing project:

```text
reuse current provider
```

New project:

```text
use configured preferred provider
```

Never silently replace an existing auth architecture.

## Auth verification

Automatically test:

```text
sign up
sign in
sign out
protected route
expired session
unauthenticated API
authorized API
role restrictions
reload persistence
```

## Security audit

Check:

```text
token storage
cookies
CSRF
CORS
session expiration
redirect validation
authorization boundary
password handling
OAuth callback security
```

Authentication being functional is not enough; it must be verified.

| Built-in authentication | 10 | **10** |
| Verification authority | 8 | **10** |
| Cancellation/recovery | 8.5 | **10** |
| Provider independence | 6 | **10** |
| Self-hosting | 4 | **10** |
| Debug transparency | 7 | **10** |

The objective is:

> **Replit-level simplicity with substantially stronger engineering discipline.**

Heidi should not simply generate more code when something goes wrong.

Its defining advantage should be:

```text
UNDERSTAND
→ TRACE
→ PROVE ROOT CAUSE
→ CHANGE
→ TEST
→ OBSERVE
→ VERIFY
```

rather than:

```text
GUESS
→ PATCH
→ ADD FALLBACK
→ ADD ANOTHER PATCH
```

That philosophy should apply to `/build`, `/debug`, `/audit`, and every specialist controlled by Heidi.
