Master Plan — FlowDeck-C-PTR
0. Objective

Build a CPTR-native implementation of FlowDeck v2.4.1's orchestration, governance, delegation, verification, evidence, recovery, and code-intelligence architecture without replacing CPTR's proven execution runtime.

The finished architecture should be:

CPTR UI / Chat
      │
      ▼
FlowDeck-C-PTR
      │
      ├─ Heidi coordinator
      ├─ canonical agent registry
      ├─ classifier / router
      ├─ governance
      ├─ delegation
      ├─ durable orchestration
      ├─ evidence
      ├─ verification
      ├─ recovery / circuit breaking
      ├─ observability
      └─ FDX adapter
             │
             ▼
       CPTR native runtime
             │
    ┌────────┼──────────┐
    ▼        ▼          ▼
 API LLMs  CPTR tools  Coding agents
                       Codex
                       Claude Code
                       OpenCode
                       Gemini
                       etc.

The implementation must port FlowDeck semantics, not its OpenCode-specific runtime wiring.

FlowDeck currently assumes OpenCode owns sessions, model execution, sandboxing and native subagent execution.

For FlowDeck-C-PTR, CPTR becomes that authoritative runtime.

3. Non-goals

The initial project must not:

rewrite CPTR chat;
replace chat_task.py;
replace Socket.IO;
replace CPTR authentication;
replace CPTR's database;
replace CPTR model providers;
replace existing external coding-agent adapters;
make OpenCode mandatory;
require Node/Bun for normal orchestration;
port FlowDeck's bun:sqlite;
give every specialist every CPTR tool;
automatically push, publish or deploy;
remove the existing CPTR agent loop;
change normal CPTR filesystem behavior globally.

This is an additive subsystem, not a CPTR rewrite.

6. Model policy

Initial rule:

one model selected in CPTR UI
            │
            ▼
           Heidi
            │
            ▼
      all specialists

Specialists inherit the selected model unless the user explicitly configures otherwise.

Do not introduce automatic specialist model switching in the first version.

This avoids debugging two variables simultaneously:

orchestration behavior;
model-selection behavior.

Per-agent overrides can come after parity is stable.

7. Capability model

Do not map specialists directly to arbitrary function names.

Create stable capabilities.

For example:

FILES_READ
FILES_WRITE
FILES_DELETE

CODE_SEARCH
CODE_ANALYSIS

SHELL_READ
SHELL_MUTATE

GIT_READ
GIT_LOCAL_WRITE
GIT_REMOTE_WRITE

BROWSER_READ
BROWSER_INTERACT

TEST_RUN
BUILD_RUN

SUBAGENT_DISPATCH

NETWORK_READ

PACKAGE_INSTALL

DEPLOY

Then map CPTR tools to capabilities.

Example:

read_file       → FILES_READ
search_files    → CODE_SEARCH
write_file      → FILES_WRITE
edit_file       → FILES_WRITE
run_command     → classify dynamically
browser tools   → BROWSER_*
git commands    → classify dynamically

This makes governance stable even if tool names change.

8. Delegation rules

This should remain strict.

Heidi
max depth = 1
may delegate to specialist
may run multiple independent specialists
Specialist
max depth = 0
cannot spawn another specialist
cannot delegate to itself
cannot delegate to Heidi

FlowDeck already follows this pattern.

Required checks:

SELF_DELEGATION_BLOCKED
SPECIALIST_CANNOT_DELEGATE
DEPTH_LIMIT_EXCEEDED
TARGET_NOT_FOUND
TARGET_DISABLED
CAPACITY_EXCEEDED

These should be typed failure codes rather than prose matching.

9. FlowDeck-C-PTR execution strategy

Heidi should classify each task into one of a small number of strategies.

DIRECT

For small, contained work.

Examples:

one-file bug;
simple config correction;
small documentation change.
Heidi
  ↓
CPTR tools
SPECIALIST

For a single clear domain.

Example:

backend API bug
      ↓
backend-coder
PARALLEL_SPECIALISTS

For independent workstreams.

Example:

            Heidi
           /  |   \
     mapper tester security

Only genuinely independent activities run concurrently.

SEQUENTIAL_PIPELINE

Example:

mapper
  ↓
planner
  ↓
backend-coder
  ↓
tester
  ↓
reviewer
  ↓
Heidi closure
EXTERNAL_AGENT

Used intentionally when CPTR's configured agent adapter is the best executor:

Heidi
 ↓
CPTR AgentPort
 ↓
Codex / Claude Code / OpenCode / Gemini

FlowDeck itself must remain independent of that choice.

12. Persistence

Do not port FlowDeck's Bun SQLite provider.

FlowDeck does have useful persistence concepts including repositories, transactions, retry policies and migrations.

But its concrete provider is based on bun:sqlite.

Use CPTR's existing SQLAlchemy database infrastructure.

Proposed additive tables
orchestration_runs
orchestration_steps
orchestration_delegations
orchestration_events
orchestration_evidence
orchestration_checkpoints
orchestration_approvals
orchestration_operations
Important rule

Do not overload Chat.meta with durable orchestration state.

Chat metadata may contain lightweight presentation references such as:

{
  "active_orchestration_run": "run_..."
}

but the authoritative state belongs in dedicated tables.

13. Why durable state matters

CPTR's current async subagents are deliberately process-local and non-durable.

CPTR also tracks live agent tasks in in-memory asyncio.Task maps.

That is fine for ordinary chat generation.

FlowDeck autonomous workflows require stronger guarantees.

After process death:

running process disappears
        ↓
startup reconciliation
        ↓
inspect durable operation record
        ↓
determine:
- completed?
- partially committed?
- safe to retry?
- needs verification?
        ↓
resume or fail safely
14. Idempotency

Every externally observable mutation requires a deterministic idempotency key.

Example:

hash(
  run_id,
  step_id,
  operation_type,
  canonical_target,
  normalized_arguments
)

Before running a mutation:

operation record exists?
        │
      yes
        ▼
 completed?
   ├─ yes → replay result
   ├─ unknown → reconcile
   └─ failed → retry policy

Examples that require protection:

file creation;
file deletion;
Git commit;
branch creation;
PR creation;
package publishing;
deployment;
remote API mutations.

Never rely solely on model instruction such as:

"Don't perform this twice."

It needs runtime enforcement.

15. Checkpoints

Create a checkpoint after meaningful boundaries.

Example:

   ↓

   ↓
CHECKPOINT
   ↓
mutation
   ↓
CHECKPOINT
   ↓
tests
   ↓
CHECKPOINT

A checkpoint should contain enough information to decide whether a step can resume safely.

Not necessarily enough to recreate an entire LLM context verbatim.

17. Approval model

CPTR's existing approval system remains authoritative.

There should be no first-version equivalent of FlowDeck's unrestricted global approval shortcut.

Risk categories:

Local safe

Usually autonomous:

read source
edit workspace source
run unit tests
run typecheck
inspect git status
local safe build

depending on CPTR configuration.

Approval required

Examples:

git push
force push
PR merge
npm publish
package release
production deployment
sudo
system changes
external destructive API call
credential access
Invalid / denied

Examples:

rm -rf /
escape workspace jail
specialist recursive delegation
read protected credentials without permission
malformed operation
18. Filesystem policy

This needs two distinct security domains.

Normal CPTR

Do not break existing functionality.

CPTR currently intentionally permits some absolute and home-directory reads while explicitly blocking sensitive credential paths.

FlowDeck specialist

Default jail:

canonical workspace root

Reject:

../
absolute external path
symlink escape
prefix-collision escape
workspace-root symlink escape
FDX escape

FlowDeck 2.4.1 explicitly hardened all of those classes.

Special exemptions should require explicit capability grants.

19. Shell policy

Do not classify run_command as simply "allowed" or "denied".

Implement command classification.

Categories:

READ_ONLY
LOCAL_MUTATION
EXTERNAL_MUTATION
PRIVILEGED
DESTRUCTIVE
UNKNOWN

Parse:

pipelines;
&&;
||;
semicolon chains;
$();
backticks;
redirection;
environment assignments;
shell wrappers.

The maximum risk of any nested segment becomes the command's risk.

Example:

echo "$(cat ~/.ssh/id_ed25519)"

must inherit credential-read risk even though top-level command is echo.

20. Git security

Port FlowDeck's hardened read-only Git policy.

FlowDeck 2.4.1 explicitly blocks dangerous options including:

-c
--config
--config-env
--exec-path
--output
--ext-diff
--textconv
--paginate
--no-pager

in contexts where they can undermine read-only guarantees.

Build a proper Git command classifier rather than maintaining scattered string checks.

21. FDX

Keep FDX as the high-performance code-intelligence engine.

Do not rewrite it in Python unless a later benchmark proves there is a reason.

CPTR interface
class FdxPort(Protocol):
    async def search(...)
    async def read(...)
    async def outline(...)
    async def impact(...)
    async def batch(...)

Implementation:

CPTR
 ↓
FDX adapter
 ↓
fdx serve --root <canonical-root>

Mandatory protections:

canonical repository root;
absolute deadline;
output-size limit;
process-health tracking;
structured-response validation;
graceful shutdown;
crash restart;
no unrestricted fallback;
identical jail semantics in native and fallback paths.

FlowDeck v2.4.1 made repository jail parity a core release requirement.

25. Retry policy

No blind repetition.

Attempt 1

Normal hypothesis.

Attempt 2

Must include new diagnosis or materially changed strategy.

Attempt 3

Same semantic failure:

CIRCUIT_OPEN

Then:

escalate to Heidi;
choose alternate agent;
ask user if necessary;
fail safely.

FlowDeck already contains repeated-action/circuit concepts and specialist escalation rules.

26. Failure fingerprints

Fingerprint failures by semantics, not literal text.

Example:

operation
target
error category
exit code
relevant normalized arguments

This prevents:

pytest ./foo
pytest foo
cd . && pytest foo

from being incorrectly treated as three unrelated failures when they are the same failing strategy.

27. Recovery

Startup recovery must distinguish:

RUNNING in DB + no live task

from actual active execution.

For each stale run:

acquire recovery lease;
inspect last checkpoint;
inspect operation state;
inspect repository/filesystem state;
determine whether prior mutation committed;
avoid duplicates;
mark prior attempt interrupted;
resume from next safe boundary.

Never automatically rerun a potentially committed external operation.

28. Concurrency

Use bounded concurrency.

Suggested first defaults:

Heidi:             1
specialists/run:   4
mutating agents:   1 per overlapping workspace ownership
read-only agents:  up to configured limit

Independent:

mapper + security-auditor

Potentially unsafe concurrently:

backend-coder + backend-coder editing same files

Use path/workspace leases for mutation.

29. File ownership and conflict handling

Before specialist mutation:

resolve intended path scope
       ↓
acquire lease
       ↓
execute
       ↓
verify
       ↓
release

If ownership can't be determined:

serialize mutation

Do not merge concurrent file edits optimistically in v1.

30. Heidi responsibilities

Heidi should be the only component allowed to:

decide strategy;
construct specialist graph;
retry with a different specialist;
terminate orchestration early;
synthesize evidence;
produce final closure;
determine whether user approval is needed.

Heidi should generally execute simple work directly rather than delegating everything.

This matches FlowDeck's current primary-agent intent.

31. Specialist responsibilities

Specialists should receive narrow assignments.

Example:

Allowed scope:

tests/api/**

Required output:
- root cause
- files changed
- tests
- remaining risks

They should not receive the entire orchestration master prompt unnecessarily.

39. Rollout stages
Phase 0 — Baseline freeze and characterization

Before implementing FlowDeck behavior:

record existing CPTR tests;
record chat behavior;
record agent behavior;
record tool approval behavior;
record restart behavior;
record Socket.IO events;
capture current performance.
Exit gate

No port code yet.

We know exactly what behavior must not regress.

40. Phase 1 — Contracts and registry

Implement only:

domain objects;
canonical registry;
capability model;
lifecycle enums;
error types;
configuration schemas.

No live execution.

Tests
registry completeness;
duplicate IDs;
delegation rules;
capabilities;
configuration parsing;
serialization.
Exit gate

All deterministic FlowDeck concepts represented natively in Python.

41. Phase 2 — Shadow router

Enable:

flowdeck.mode = shadow

For every eligible CPTR request:

classify;
choose strategy;
choose specialist graph;
evaluate governance;
log result.

Then:

discard FlowDeck decision

and allow existing CPTR behavior to execute normally.

Exit gate

Large fixture suite demonstrates routing consistency without changing user behavior.

42. Phase 3 — Durable run engine

Build:

steps;
event journal;
leases;
idempotency;
recovery.

Still no real specialist mutation.

Failure tests

Kill backend during:

classification
step startup
checkpoint
step completion

Then restart.

Exit gate

Run integrity remains correct.

43. Phase 4 — Read-only specialists

Enable:

search;
inspect;
FDX if available.

Denied:

45. Phase 6 — Tester

Exit gate

TDD/regression workflows work safely.

46. Phase 7 — Coding specialists

Progressively enable:

debug-specialist;
browser-debugger;

Not all at once.

    ↓

Enable:

flowdeck.mode = full

only after prior stages have passed.

Now Heidi may autonomously:

repair;

But external sensitive actions still require CPTR approval.
